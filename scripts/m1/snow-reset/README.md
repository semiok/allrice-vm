# 两人清零演练

演练使用同仓迁移创建合成数据，做 `pg_dump` 后恢复到专用 Unix socket 上的新库，再核对还原前后的全部业务表。入口只接受合成数据，数据库名固定为 `snow_reset_restore`，PostgreSQL 禁用 TCP。提交对应的 M5 命令如下。

```sh
m5-test <commit> --on m5 --db --build 'python3 scripts/m1/snow-reset/rehearse.py && pnpm build:test-sources' -- scripts/m1/snow-reset/vm.test.ts --maxWorkers=1
```

合成组织为 `00000000-0000-4000-8000-000000000001`，工作区为 `00000000-0000-4000-8000-000000000005`。SQL 只接受下列完整清单。开始每一阶段时，它逐项核对输入、用户 UUID、精确 username、活动用户及有效的组织和工作区成员关系。

| 账号   | 合成 username | 合成用户 UUID                          |
| ------ | ------------- | -------------------------------------- |
| snow   | `snow`        | `00000000-0000-4000-8000-000000000002` |
| 验收员 | `acceptance`  | `00000000-0000-4000-8000-000000000004` |

## 执行顺序

1. 对两人分别计算待删除行族。按本人和工作区选择实例、派驻、个人配置、会话和 Run，沿实际入向外键和已审的消息 Memory 关系追踪从属行。个人员工源须匹配 `personal-<id>` 与本人自派驻。跨人归属或父项、跨工作区员工、未知从属和活跃 Run 或 job 会中止此次事务。保留行的 D entry claim 和 root、旧版原生根及会话绑定、员工 Memory 上下文或原生调度观察回执引用待删对象时，也会停止。
2. 清除 snow 的业务行。计划前后核对全库行多重集。清除保持灰度原行、验收员及其他账号、工作区和组织、登录及凭据记录、共用员工源、对象与访问授权原样。外键持续启用。事务只暂停四个已审删除拦截器，并在提交前恢复。后段注入失败会回滚数据及触发器状态。
3. 确认 snow 业务为零，锁定系统灰度行并比对审批时的完整 JSON。一次提交把两人的旧三元组改为各一条按人项，保持 `3.x` 默认及其余兼容条目的内容和顺序。发现他人旧三元组、审批快照已变化或缺少目标身份就中止。已切换的名单再次执行保持 revision 不变。
4. 以切换事务提交后返回的完整策略 JSON 为预期值，锁住同一灰度行并确认 revision 与名单全等，再清除验收员业务行，另核空计划及全库对账。业务清零只读取 VM 生命周期表用作前置检查。正式清零还需要 Host 的独立物理证明。

VM 用例调用真实 `PersonVmService.delete(context, { deleteDisk: true }, signal)`，在同一租约内比对组织、本人、VM、实例和 epoch。用合成存储和原生端口验证两个目标定向删盘、保留第三人、错误绑定、未知原生状态、独立删盘授权和重复执行。使用的状态、挂载、磁盘及审计均为模拟数据。

## 正式交接

正式执行需由发布负责人拿到经过批准的两个实际身份及确切发布 SHA。验收员的角色名和合成 username 无法证明真实 username。取得可审计的用户名、用户 UUID、组织和工作区 UUID、活动成员关系及旧灰度证据后，再从 M1 受保护的最新备份清点实际关联并验证回滚。盘、密钥和原生配置另行备份并验证可恢复。保持本次两人和灰度的独占写入窗口，盘阶段成功后才执行对应的业务事务。当前无外键检查覆盖源码可定位的路径，正式库存还须核定未知关联、对象、ACL、工作流、定时、审批及插件，分清数据引用与不可变审计快照，并交相应 owner 裁定。

`apps/worker/src/person-vm/production-authority.ts` 当前仅授权读、建、启动。`ProductionPersonVmHost` 和私有 recovery socket 没有受权的定向停机及删盘口。负责 Host 的 owner 须提供在当前租约内校验 `(organizationId, personId, vmId, instanceId, leaseEpoch)` 的受权入口，调用现有 `PersonVmService.delete` 并保留审计。该方法接受 `stopped` 作为停止证据，完成后仍须独立核对 native 实例、挂载、盘和密钥、端口、租约及可消费 wake。真实盘阶段未核清前，正式流程停在前置核对。

现有三阶段、行族及回执全部属于合成恢复库。正式的 dry-run、apply、verify 和已提交后的按人恢复命令由发布负责人和相关 owner 在上述前置到齐后，绑定实际发布 SHA 提供。灰度回退也须比对当前 revision 和完整名单。业务事务内失败与已提交后的盘及数据恢复分别取证。
